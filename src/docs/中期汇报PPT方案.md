### P2 | 行业痛点：农业采摘为什么难自动化?

**核心矛盾：传统机器人在受控实验室表现良好，但进不了真实的田。**

三点痛点：

1. **环境非结构化**
   - 枝叶遮挡密集、光照多变、目标形态差异大
   - 传统视觉算法基于封闭训练集，泛化能力弱。换个品种、换片田，模型就失效。

2. **缺乏语义常识**
   - 传统系统将所有障碍物一视同仁——全部绕行
   - 实际场景中，软质枝叶可以推挤、树干必须绕行，缺乏这种判断导致规划频繁失败

3. **现有方案的困境**
   - 传统方案 (YOLO + RRT)：泛化差，遮挡场景需外加物理吹风装置辅助
   - 端到端大模型 (RT-1/RT-2 VLA)：算力成本高、决策不透明、物理碰撞风险大
   - 两难：要么不够聪明，要么不够安全

> 配图建议：真实农田遮挡/簇生场景照片 vs 实验室干净环境对比

### P3 | 技术现状

**传统目标检测 + 经典运动规划（主流方案）：**

- 代表：刘旭赞等垄作草莓双臂采摘机器人 (2026)，YOLOv8-seg + RRT
- 温室无遮挡条件采收成功率 88.1%
- 局限：严重遮挡时成功率大幅下降，需外部物理吹风辅助

**端到端 VLA 大模型（前沿探索）：**

- 代表：RT-1 (2022) / RT-2 (2023, VLA) / PaLM-E (2023)
- 零样本泛化能力强，从图像直接映射到动作
- 局限：百万级演示数据需求、算力成本高、决策不可解释、物理安全性难保证

**混合分层架构（最新趋势）：**

- 代表：SayCan (2022) / PaLM-E (2023)
- VLM 做高层语义理解 → 传统控制做底层安全执行
- 兼备泛化能力与执行安全性
- **局限：在农业垂直场景中缺乏验证——2D语义到3D空间映射的精度与鲁棒性问题尚待解决**

> 配图建议：横轴 "感知能力"，纵轴 "物理安全性"，标出三个方案的位置

### P4 | 课题意义

**回到本质问题：** 能不能用大模型的常识推理 + 传统控制的确定性执行，在仿真环境下先跑通"看懂场景 → 做出判断 → 安全执行"的闭环？

**三个具体目标：**

1. 验证 VLM 在非结构化农业场景中的语义决策能力（软硬障碍物辨识、零样本目标筛选）
2. 打通 2D 视觉语义 → 3D 安全轨迹的完整映射链路
3. 构建一个低成本、可在仿真中完整验证的技术方案，降低真实系统试错成本

**适用范围：** 不仅限于草莓采摘——软硬障碍物分类+推挤排障的策略可迁移至其他柔性对象操作场景

### P6 | 核心技术点 1：双阶段 VLM 推理

**问题：** 单次 VLM 推理在全局视角和局部精度之间难以兼得。

**方案：双阶段串行推理**

| | 阶段一 (Stage 1) | 阶段二 (Stage 2) |
|---|---|---|
| **目的** | 全局场景粗定位 | 末端近距精定位 |
| **相机** | Gemini 335 (俯视) | ee_camera (手眼) |
| **视角** | 广角全局 | 贴近目标 |
| **输出** | 目标果实 bbox | 果柄精确 bbox |
| **发布位姿** | /target_pre_grasp | /target_pose |

**触发条件：** 阶段一完成预抓取姿态后，机械臂已靠近目标，此时手眼相机视图清晰 → 阶段二精确定位果柄

**关键设计决策：**
- VLM 选型：Qwen3 VL Plus (DashScope) — 中文能力强、JSON 输出稳定、归一化[0,1000]坐标易于转换
- Prompt 工程：约束 JSON schema、归一化坐标规范、无目标返回[-1,-1,-1,-1]的明确失败语义
- 线程安全：Lock 守卫状态机 + 主线程发布消息，VLM 调用放 worker 线程避免阻塞 ROS 回调

> 配图：阶段一/二相机实拍图 → bbox标注 → 3D坐标 的流程示意

### P7 | 核心技术点 2：2D语义 → 3D安全轨迹的映射链路

**核心挑战：** VLM 只在 2D 像素空间输出决策，机械臂需要基坐标系下的 3D 位姿。

**映射链路 (5步)：**

1. **VLM 输出 bbox** → 归一化坐标[0,1000] → 实际像素坐标
2. **深度查询** → bbox 区域最小深度（排除地面背景，确保取目标顶部而非穿透过深）
3. **针孔反投影** → 像素(u,v) + 深度 Z + 相机内参 K → 相机光学坐标系 (X,Y,Z)
4. **TF2 坐标变换** → camera_optical_link → base (机械臂基坐标系)
5. **发布 PoseStamped** → grab_action 接收执行

**两个关键设计细节：**
- 深度取值策略：bbox 区域内 min depth 而非单点查询——单点可能命中背景，min 取目标表面最近点
- 双相机两套内参：阶段一用 Gemini 335 的 camera_depth_optical_frame → base，阶段二用 ee_camera_optical_link → base

> 配图：像素坐标 → 3D空间 映射示意，标注各步骤的坐标系

### P8 | 核心技术点 3：9阶段抓取状态机 + 双层附着

```
IDLE → SETUP → PRE_GRASP → AWAIT_STAGE2 → APPROACH → GRASP → LIFT → TRANSPORT → PLACE
```

**每个阶段的关键操作：**

| 阶段 | 操作 | MoveIt/PSM 状态 |
|------|------|----------------|
| SETUP | 注册目标物体到 Planning Scene | 物体=碰撞体 → MoveIt 自动绕行 |
| PRE_GRASP | 规划上方预抓取位姿 | 不碰到物体 |
| AWAIT_STAGE2 | 等 VLM 精定位或超时降级 | - |
| APPROACH | 张爪, 移除物体碰撞体, 下移 | 不再避让目标（已在手中） |
| GRASP | 闭合 + 双层附着 | Gazebo AttachLink + MoveIt attach_object |
| LIFT/TRANSPORT | 抬起+搬运 | 物体附着自动防碰 |
| PLACE | 双层脱离+张爪 | detach + 清理 |

**"双层同步"机制：** Gazebo 物理引擎的 AttachLink 保证物理真实 + MoveIt 的 attach_object 保证后续路径规划知道物体已附着 → 避免物体被"撞飞"

> 配图：状态机流转图，标注每个阶段的触发条件和操作

## 四、目前碰到的问题 (2页)

### P14 | 当前主要问题 (按严重程度排列)

**1. APPROACH 阶段自碰撞 (高)**

- 现象：fix_start_state_collision 报告 shoulder-upper_arm 相邻关节碰撞
- 已尝试：ACM 禁用碰撞对不生效，增大 jiggle_fraction 不解决问题
- 影响：部分姿态下抓取接近阶段规划失败

**2. PSM ApplyPlanningScene 服务超时 (中)**

- 现象：rclpy Client 调用 /apply_planning_scene 服务始终超时，但手动命令行调用成功
- 已尝试：MultiThreadedExecutor + time.sleep 循环可维持回调链路不断，但 service 响应仍无法被 client future 捕获
- 当前策略：PSM 超时仅 warning，fallback 到旧行为继续抓取

**3. MoveIt SRDF 碰撞禁用不完整 (中)**

- 机械臂与 bed/plant/dirt 的 collision pair 未禁用 → 工作空间受限

**4. Joint 5 越限 (中)**

- 特定姿态下关节 5 超过 URDF 限位 -2.79 → -2.95 rad
- 当前为开环控制 (open_loop_control=true)，无反馈修正

**5. 控制系统精度 (中)**

- arm/gripper controller 均为开环模式
- 可能影响抓取精度和重复性

### P15 | 问题分析与应对思路

| 问题 | 短期应对 | 根本解决思路 |
|------|---------|------------|
| 自碰撞 | 调整预抓取姿态偏移方向 | 研究 MoveIt ACM 生效条件，或换用不同 IK 求解器 |
| PSM 超时 | fallback 到 topic 方式 (已实施) | 排查 rclpy service call 的 executor 调度机制 |
| SRDF 碰撞对 | 手动补充 ACM entries | 排查 SRDF 生成流程 |
| Joint 5 越限 | 在规划请求中加 joint limits | 排查 URDF limit 参数与 IK 结果的一致性 |
| 开环控制 | — | 评估是否需要闭环（Gazebo 中 joint_position_controller 可闭环但调试成本高） |
